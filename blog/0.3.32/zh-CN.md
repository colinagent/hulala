## 按下 y 之后卡住的提示

你在远程开发机上干活。窗口是 `hulala ssh dev`，模型请求往工作区外写一个文件，
审批卡出现在对话底部。你按下 `y`。

卡片消失了，命令没有开始。底下提示连接断开，这一轮就停在那里：没有报错，也没有
结果。Host 那边仍然把这次审批标成等待中；工具在等一个永远不会到达的决定。

问题不在你按错了键。审批的回答并不是顺着送来问题的那条 socket 走回去的，客户端
会把它作为一次 HTTP POST 发给 Host。走 ssh 转发时，这次 POST 可能正好落在转发重建
的窗口里，也可能在换了 cookie 之后到达：HTTP 这边拿着新的 Host 身份，事件流那边
的 socket 还是旧身份。Host 拒绝这个结果，客户端又把拒绝当成事件连接坏了，于是整条
流被拆掉。审批卡、正在等回答的问题、工具状态一起不见了；Host 上那条待审批没有人能
再回答。

这也是为什么重连之后再按一次 `y` 有时有效、有时没用。卡片回来了，但 HTTP 和 socket
不一定回到同一个身份上。

## 保住答案，而不是保住连接

0.3.32 改了两件事的顺序。第一，mux socket 还活着的时候，客户端不再换 Host 凭证。
如果换凭证和重连撞在一起，就替换 socket，让 HTTP 和事件流重新说同一个 Peer 的话。
这是把拒绝本身去掉，而不是等拒绝发生后再补救。

第二，审批答案本身现在会被记住。客户端按工具调用 id 存下你的选择。如果传输在 Host
收到结果之前断了，Host 会保留这条待审批，并在下一条事件流上重放它。客户端认出同一次
调用，把同一个选择补发过去，然后才让卡片离开。选择的是本会话完全权限也一样：`f`
只需要按一次，重连后不需要再按。

审批结果的 POST 还加了十秒上限。一条接受连接然后沉默的转发，过去会把答案挂在那里
好几分钟，看起来就像 agent 卡死了。十秒对一次本机 POST 已经非常宽裕，又短到足以结束
这一代连接、重连并重放审批。

如果一张卡片的投递真的断了，对话里现在会提示它会回来。这句话很小，但它区分了两种
完全不同的状态：工具在思考，和工具在等一张已经消失的卡片。

## 整个会话的选项放进底部

这次发布的另一半，是一个早就存在、但很难找到的选择。从 0.3.19 开始，审批卡里的 `f`
会执行 Host 的 `/permission danger-full-access`：沙箱不再限制文件写入，本会话的审批
策略变成 `never`，后面每一轮都不再询问权限。新会话仍然使用各自的默认值。

变的是它出现的位置。以前它只是卡片正文里一行暗色说明，底部的选项只有允许一次、拒绝
和取消。现在底部是：

```text
[y] allow once  [f] whole Session  [n] reject  [Ctrl-C] cancel
```

上面的说明会告诉你，本会话后续轮次不再询问。选择它仍然会先放行当前这一次调用，
再切换会话，所以你正在批准的操作会执行，下一次不再问。想恢复随时可以
`/permission workspace-write`。

适合用它的情况，是这一整段对话确实都在工作区外干活：部署目录、系统服务、放在仓库
旁边的配置文件。不要把它当成默认设置。它是一个会话级的开关，下一个会话仍然从你
配置的默认值开始。

## 怎么看到它

更新，连到一台机器，然后让它往工作区外写一个文件：

```sh
hulala update
hulala ssh dev
```

审批卡出现。按 `f`，这条命令照常执行；下一条需要同样权限的命令不再弹卡。想把询问
要回来，在输入框里执行 `/permission workspace-write`。

重连路径不太容易故意复现，能观察到的是这一段：在一个会话正等审批的时候停掉 ssh
转发，再让它恢复。卡片会带着提示消失，Host 重放待审批时它回来，你之前的选择会在
不需要第二次按键的情况下发出去。如果机器离线超过十分钟，客户端就不再相信那个旧
答案，会重新问你；选择不会被永远记住。

还有一个限制值得说明。这次发布让答案能挺过一次断开的连接，但它不会把一台真的下线的
机器变回来。如果 Host 进程不在了，卡片会一直等到 Host 回来，和任何其他会话状态一样。
